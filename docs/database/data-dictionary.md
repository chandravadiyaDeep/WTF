# NUMPA v2 — Candidate Data Dictionary

**Status:** Design catalog for review, not executable DDL or a migration. Names and constraints are PostgreSQL proposals; no schema has been created.

## PostgreSQL conventions

- Unless stated otherwise, an application table has id uuid NOT NULL PRIMARY KEY DEFAULT gen_random_uuid() and created_at timestamptz NOT NULL DEFAULT now(). Tenant-owned tables also have workspace_id uuid NOT NULL. Times are UTC instants.
- Suffix ? means nullable; without ? means NOT NULL. PK, FK, UQ and CHECK columns below are actual proposed constraints. JSONB fields are bounded, versioned documents validated by application/database routines; do not use them as unvalidated references.
- Every workspace-scoped FK should be enforced as a composite relationship: parent has UNIQUE (workspace_id,id), child FK (workspace_id,parent_id) REFERENCES parent(workspace_id,id). This prevents a valid UUID in workspace A from pointing to a resource in workspace B. Child tables that do not repeat workspace_id may use a direct FK through a parent already scoped to the same workspace.
- UUID application IDs, bigint bytes/counts, integer token units, numeric measured model scores, text codes/statuses with CHECK constraints, and integer minor currency units are real PostgreSQL types. “Validate JSON schema” and “job target matches type” are semantic checks requiring a trigger/function or trusted backend; they are not native CHECK syntax over arbitrary application logic.
- All workspace tables enable RLS; policy matrix and write authority are specified in the architecture plan. created_by/requested_by records actor attribution and never grants access.
- Retention is policy-dependent; no durations are approved. “Source/dependency policy” means deletion is coordinated and surfaced to the user.

### Billing invariants and transaction boundary

Define **total_tokens** as net credited purchased/promotional/bonus/referral tokens less captured spend/refunds; **reserved_tokens** as unspent holds for active reservations; **available_tokens = total_tokens - reserved_tokens**. Wallet values are a cache only. The authoritative event history is immutable posted ledger entries plus reservation state; reconciliation recomputes expected total and active holds and flags discrepancy. If exact source balances or expirations are required, add token lots/credits as a reviewed extension before implementation rather than pretending a single wallet models expiry.

For reserve, capture, release, purchase credit, and refund: use one PostgreSQL transaction or narrowly scoped security-definer routine with fixed search_path. Lock wallet row (or use serializable isolation), validate available funds, write reservation/ledger and update wallet cache atomically. Unique idempotency keys are per logical event, e.g. (workspace_id,job_id,operation) for reserve, reservation+capture sequence for capture, provider+event ID for payment. Payment webhook signature verification and deduplication precede one unique credit. Repeated job attempts share job/reservation and cannot capture again. A unique transition key plus allowed-state check rejects double capture. Terminal job and settlement transition are committed together; no client can write financial tables. Database transactions cannot include external worker execution or payment network calls; use durable states/outbox and idempotent callbacks.

## Immutability enforcement (proposal)

Published pipeline/readiness versions and completed run/result records are protected by database privileges that deny UPDATE/DELETE to client roles, narrow backend transition routines, and (where defense-in-depth warrants) triggers rejecting mutation after published/terminal state. Grant insert to trusted backend only for outcome tables. Corrections create a new version or compensating audit/ledger record; do not edit old evidence or metrics. Referential FKs and delete-restrict behavior preserve provenance; a separate deletion workflow first revokes access, then removes dependent objects/rows according to approved policy. These controls require migrations and security review later; this document does not claim they are already active.

## Required relationships and same-workspace integrity

- Workspace rows are the tenant boundary; member access is from workspace_members. Every child records workspace_id for RLS and composite FK checks.
- Dataset asset/version, run, cleaning, readiness, experiment, training, report, and billing parents must match workspace_id. A UUID alone is never sufficient authorization.
- Reports should use typed report-source join rows for query-critical provenance (run/version/comparison); arbitrary JSON IDs are display snapshots only.
- Completed ML outputs capture dataset version, experiment configuration/protocol hash, algorithm/software version, split roles, and metric definition/version.
- Version/config changes create new rows. Published versions and completed results are protected as above.
