# NUMPA v2 — Storage and Retention Matrix

**Status:** Draft for review. Retention durations, regions, legal holds, deletion SLAs, backup windows, and recovery objectives are open decisions. “Until source deletion/policy expiry” is a dependency rule, not an approved period. Cloud records must not be created for browser-only bytes by default.

## Lifecycle rules

1. **Private by default:** no public bucket for user data. An object key is not permission.
2. **Database/object coordination:** upload and delete span PostgreSQL and object storage and are not one transaction. Use pending states, idempotent workers, retryable deletion, and reconciliation of missing/orphaned objects.
3. **Authorization:** check workspace membership and object metadata before issuing short-lived signed URLs. Storage policies must also restrict direct access. Never expose the service-role key or log signed URLs.
4. **Lineage deletion:** explain whether deleting a source also removes cleaned versions, reports, and model artifacts. Block new access immediately, cancel work, then physically delete dependent objects and update status.
5. **Browser truthfulness:** clearing browser storage, quota eviction, browser profile changes, or device loss may destroy local data. Do not imply cloud recovery unless the user chose cloud persistence.
6. **Data minimization:** store summaries and provenance instead of row-level copies; sanitize worker errors; avoid sensitive sample values in logs, evidence, and reports by default.
7. **Policy approval:** choose retention periods, region, backups/PITR, recovery objectives, deletion SLA, and legal exceptions before production implementation.
